# Features, testing status and limitations

Status key: **Done**: implemented and covered by automated tests. **Done (needs live check)**: implemented and tested with
mocked external services; it needs a real key or network on the demo PC to confirm. **Needs data/training**: the code is ready,
but it only works once a model or dataset is produced on the PC.

## Expanding the food classes (not done in this build)
Retraining was not performed; no new labelled dataset was available, and recognition coverage has **not** increased.
The pipeline for it already exists: `prepare_splits.py` (leakage-aware splits), `train_food_classifier.py` (head and fine-tune),
`calibrate_rejection.py`, and `diagnose_recognition.py`. To add foods:
1. Collect at least 300 licensed images per new class (e.g. Food-101 and Indian-food datasets with permissive licences), plus reviewed user corrections.
2. Re-run `prepare_splits.py` (dedupe + group split), then train, evaluate on validation (per-class precision, recall and F1, macro F1, confusion matrix), and recalibrate.
3. Back up `models\production\food_classifier` before replacing it; evaluate on the test split once, with approval.

## Known limitations
- The classifier knows 24 foods; unsupported foods can still be confused with similar supported ones. Agreement checks and Vision reduce this but cannot eliminate it.
- Non-food rejection has only been evaluated on packaging images; general non-food performance is unknown.
- Nutrition values are reference data per food type (USDA), not measurements of the photographed item.
- OCR can misread digits, especially on curved or glossy packs; dates and nutrition from OCR are shown "as printed".
- A photo cannot detect microbes, toxins, pesticide residues, heavy metals or adulteration.
- External services (OpenAI Vision, Google Vision, Gemini, Open Food Facts, PubChem, FDC) were tested only with mocked responses in the build environment.
